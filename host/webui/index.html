Your pad

How this page works

WebUSB — Web Serial — Web MIDI —

The page talks to the pad itself: lights over MIDI, backups and flashing over the USB DFU bootloader, the 1200-baud reset over the serial port. Nothing runs on this computer except the browser. Chrome asks once per browser profile for each device — select the serial port while the pad runs the app, and the DFU device while it is in bootloader mode.

Build firmware (GitHub Actions)

Firmware cannot be compiled in a browser. Copy the settings JSON, open the workflow, run it with the JSON pasted into settings_json, then download MidiFighterSpectra.bin from the finished run and flash it on the Upload tab.

Application backup

Reads the running application area over DFU (alt 0) and saves it in your Downloads folder. Flash it back from the Restore tab.

Full flash backup

Reads all 512 KiB raw over DFU (alt 1, read-only) and saves it in your Downloads folder. For archival: restoring a raw dump needs the Pico ROM flow and is not offered here.

Restore an application backup

Flashes an app-area .bin over DFU alt 0 — a backup you downloaded here, or a firmware build from GitHub Actions. The file is validated in the page before any USB traffic, and the bootloader checks it again and writes its directory last, so an interrupted restore leaves the pad in the bootloader instead of half-flashed.

Full-flash dumps are read-only archives: restoring one requires the Pico ROM download flow (host/flash_fw.sh stock on macOS, or tools/jl-uboot-tool on Linux).

Upload application firmware

Pick a built app-area .bin (a directory + app.bin + cfg_tool.bin, e.g. MidiFighterSpectra.bin from the Actions build). The file is validated before flashing.

Force the bootloader open

  1. The Pocket has no buttons: with its application running, Reboot into DFU above sends the 1200-baud touch and it reboots as DFU 1209:0002. (The SK12 reference board can also be powered on with SHIFT + PLAY held; its SHIFT LED then blinks.)
  2. An application that crash-loops is caught by the bootloader after four unconfirmed boots; a failed application CRC keeps it in DFU the same way.
  3. If the application still runs, this page can reboot it into the bootloader (Reboot into DFU, or any backup/restore).
  4. Chrome asks once per profile for the DFU device: use Select DFU device on the Status tab.

Restore the application

Fetches the application build shipped with this page, checks its SHA-256 and the directory/area CRCs, then writes it over DFU alt 0. It works whether the pad runs the application or sits in the bootloader; if it runs, the page reboots it into DFU first. An interrupted write leaves the pad in the bootloader, where this button works again.

Repair the bootloader

Writes the bootloader through DFU alt 2 and performs the two sector-0 pointer writes — the riskiest windows in the whole system. Keep the USB cable connected and the pad powered.

recovery/boot_update.bin — details not loaded yet

This only helps a bootloader that still runs DFU. A pad that never appears as 1209:0002 is in ROM download mode — see below.

Dead bootloader: ROM download mode

If the pad stays dark and never appears as 1209:0002 or 1209:0001, the chip may have fallen back to its ROM download mode (USB 4c4a:2542, BR25 UBOOT1.00). That device is USB mass storage, which Chrome never lets a web page drive, so this page cannot write it. The host tools can, with a Raspberry Pi Pico on the USB data lines (hw/jl-usbkey):

  1. Power the pad off. Flash hw/jl-usbkey to the Pico once, open its serial console and send r.
  2. Power the pad on. The Pico sends the USB_KEY, then releases the bus; the pad enumerates as 4c4a:2542.
  3. Look before writing — status and a full backup:
host/maskrom.py status          # classify the flash, diff the factory image
host/maskrom.py backup          # all 512 KiB raw, into work/recover/
  1. Then either the factory firmware, or this project's bootloader followed by a DFU application flash:
host/maskrom.py restore-stock   # factory firmware, 0..0x75000, byte for byte
host/maskrom.py install-boot    # bootloader at 0x1000 (+ sector 0 if it drifted)

Every write backs up the flash first and is read back sector for sector; the pad's data above 0x75000 is never touched. The factory image is your own dump (dumps/original_physical_full.bin) and stays off this site. Never write the vendor .fwsc container. After install-boot, power-cycle the pad and use the restore button above.

Bootloader update (advanced)

This rewrites the bootloader through DFU alt 2. The package is verified before the two sector-0 pointer writes — the riskiest windows in the whole system. Keep the USB cable connected.

Bootloader mode

If a failed write left the pad in the bootloader, this boots the application again (DFU detach).
